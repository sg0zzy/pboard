# Google and Drive authorization refactor: initial audit

Status: investigation and isolated codec only; the production security protocol has not changed. This document does not authorize deployment.

## Current dependencies

| Area | Current implementation | Required direction |
| --- | --- | --- |
| Google credentials | Firefox uses OAuth authorization code with PKCE and a stored refresh grant; Chromium uses `identity.getAuthToken`; Android uses Google Identity Services authorization. The common interface returns a Drive access token, not an ID token. Existing scopes include Drive and legacy appData. | Obtain a server-verifiable stable Google subject and validate the permitted OAuth clients on all platforms. Keep delegated tokens short-lived and out of logs and URLs. |
| Relay session | `/identity/exchange` verifies Google identity and issues a short-lived, device/challenge/session/room-bound ticket. Separately, relay admission requires a signed manifest or operator grant. | Replace the independent grant with server-verified Google identity and Drive authorization; preserve challenge binding and session isolation as appropriate. |
| Board authority | Browser-held authority keys sign device manifests; the relay verifies them and a service ticket. Drive permission is checked in client paths, but is not the sole relay admission authority. | Verify the effective Drive role at the relay for each board, independently of a device roster. |
| Account channel | Its authority manifest lives in appData and a particular browser holds its signing key; that browser must renew expired manifests and help with key distribution. | Replace account-room identity and discovery with Google subject based admission, without appData or a browser authority. |
| Encryption | Relay operation payloads use AES-GCM and a board content key stored in a separate IndexedDB database. The authenticated courier wraps keys to other devices; a joining device can wait for an existing key holder. Legacy buffer/leader paths also use these keys. | New relay payloads use a versioned plaintext envelope, with validation and corruption detection. Keep legacy readers and keys until all relevant history is safely covered. |
| Drive data | Current operation snapshots and immutable operation segments are JSON with validation and integrity hashes. Assets are stored as Drive files and checked by content hash. The older `board.json.gz` and legacy shared `project.json` layouts remain compatibility inputs. | Retain durable formats and immutable history where possible; distinguish them from encrypted relay rows. Audit all legacy paths before claiming every historical format is plaintext. |
| Infrastructure | `../vps-maint/SERVICES.md` records a loopback relay behind TLS-terminating HAProxy and a restricted route allowlist. Its observations are dated and do not prove the current remote configuration. | Coordinate proxy routes, accepted OAuth audiences, relay binary, migration, rollback and clients; do not deploy an incompatible partial change. |

## Migration and compatibility risks

The relay can contain acknowledged encrypted operations that are not yet represented in Drive. A current Drive snapshot alone does not prove their preservation. Migration must establish an enforceable server-side write barrier for old clients, drain the legacy relay through a device holding the right key, publish immutable Drive data, verify readback and operation coverage, and only then enable a separately versioned plaintext stream. An unavailable key or missing relay history must be reported as unresolved; neither data nor keys may be deleted. Offline old clients need a protocol rejection that preserves their local outbox and a supported upgrade path. Concurrent attempts need a server-enforced generation or equivalent atomic fencing, not a Drive filename lock.

The plaintext codec introduced alongside this audit **is now the production codec** for every Drive-authorized room: `runtime.ts:2650` (board log) and `accountChannel.ts:796` (account room) select it whenever the auth provider supplies Drive identity credentials. That is the condition the paragraph above asked for — the room is admitted by Google's verification of the account and the Drive folder, not by a device-manifest content key — so no migration of an existing encrypted room was needed: the signed path keeps `createOperationLogCodec` and its content keys, and the two never share a room identity. Its digest detects accidental corruption; it is not an authentication mechanism, and the relay's admission is what makes accepting these rows safe.

The local relay includes a migration fence. It atomically captures the current sequence, rejects new operations while preserving duplicate acknowledgments, survives a restart and suspends pruning for the fenced board. Local protocol actions can start or cancel a fence for an owner admitted by the current manifest-backed mechanism; role-less operator grants cannot do so. The local operation-log client can send these actions over its existing socket and validates the replies. This is only an intermediate path: it lacks Drive-based authorization, a cutover path and a wired migration workflow, and must not be treated as a usable migration. Its database schema is version 4: the previously deployed version-3 relay cannot open an upgraded database, so deployment needs a tested database-compatible rollback before activation. The live relay has not been upgraded to this schema.

Local implementation now also contains an IndexedDB-backed migration reservation and intent journal and an opt-in Google verifier. The verifier checks Google RS256 ID-token signatures, issuer, configured audiences, expiry and subject, then matches the delegated Drive token's userinfo subject and checks folder capabilities. It includes the folder ID in its room identity. Local socket admission consumes one-use tickets and supports renewal; a room expires after at most 120 seconds without another successful verification. This path is not active in the deployed relay, and browser OAuth providers do not yet supply its required ID token and OpenID userinfo scope. Board-access caching, integrated client renewal and real Google/Drive testing remain outstanding. No legacy key or data has been removed.

The relay now carries the owner role from its existing verified room admission into synchronization requests and refuses consolidation lease and checkpoint commits for manifest-backed editors. Role-less legacy operator grants retain their old consolidation access for compatibility. This is not Drive-based authorization: the current owner role still comes from the legacy admission manifest. The future authorization replacement needs a coordinated rollout and a recovery plan for operator-grant installations.

## Remaining design and implementation work

* Establish a trusted logical-board-to-folder binding for all current and legacy layouts, including duplicate folders and shared-with-me discovery. A folder name alone is not a global authority for a logical ID.
* Define delegated access-token validation and obtain a stable Google `sub` without assuming an ID token exists on every platform. Verify token audience/client and identity binding against Google. Determine exact role capabilities from live Drive metadata, including inherited access and quota errors.
* Add bounded, single-flight authorization caching and fail-closed expiry. Active subscriptions must be detached within a defined interval even when revalidation fails. Explicit invalidation must be bound to a verified sharing change, not a client assertion.
* Integrate role checks into every relay subscription and operation, including owner-only checkpoint, compaction and administrative actions. The current sync request path includes lease and checkpoint operations whose existing writer checks must be revisited.
* Design a protocol with one persistent multiplexed socket per client and authenticated renewal, alongside safe legacy coexistence and rollback. Cover Android and both extension OAuth implementations.
* Implement and test fenced migration, missing-key recovery, interrupted and concurrent attempts, offline clients, replay and plaintext format selection. Preserve legacy key recovery until coverage is established.
* Verify actual proxy configuration, rate limits, accepted public OAuth client IDs and deployment state before preparing the coordinated rollout. No remote deployment is authorized by this audit.
